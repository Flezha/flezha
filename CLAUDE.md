# Flezha repo notes

Detailed per-change implementation notes (gotchas, load-bearing decisions, test
maps) live in `docs/dev_notes/<change-id>.md` — one file per OpenSpec change.
Before touching an area listed below, READ its notes file first; the gotchas
there are deliberately not repeated in `docs/`.

Maintenance rule: when a change lands, write its notes to
`docs/dev_notes/<change-id>.md` and add ONE index line here (newest first).
Never inline the notes in this file — it must stay small enough to load whole.

Cross-SDK rule: there is no such thing as a Rust-only SDK change. Any surface
every SDK carries — the authoring/declaration surface, the `HostClassDecl`
keys, the wire protocol, a default (overflow, retry ladder, mailbox, heartbeat
keys), a bench or e2e fixture — changes in Rust, Java AND Elixir in the same
change, or the change names the SDK it defers and the follow-up that owes it.
`flz_core` is shared by Rust and Java (JNI) only; the Elixir SDK is its own
core and inherits NOTHING from it. A perf number measured on one runtime is
proven on one runtime. Normative text and the per-SDK matrix:
`docs/architecture/runner.md` → "One change, every SDK".

## Per-change notes index

- [Open-source licensing](docs/dev_notes/open-source-licensing.md) — MPL-2.0 controller + Apache-2.0 SDK side; the Elixir SDK split exists ONLY in `REUSE.toml` (no per-file headers); `flz_transport` must stay Apache (shared by `flz_nif`); `process_hub` must never regress to GPL (`make refresh-process-hub` unlocks the pin); jar notices ride the shade `IncludeResourceTransformer`, the colliding upstream `META-INF/LICENSE`/`NOTICE` are filtered and reproduced in `THIRD_PARTY_NOTICES.md`, which `cargo about` generates and CI diffs; nothing is published yet
- [Workflow durable-path throughput](docs/dev_notes/workflow-durable-path-throughput.md) — a batched append is a deferred reply and the token is the `send_request` id; ONE writer facility (`dedup: true` on the 16-byte header) gives both the idempotent re-send and the inbox window; the commit worker never waits on a writer — cuts are casts and a cut below 64 KiB is deferred (inline cuts cost 40–97 ms per turn); only a class with no compensable procs is cut; the "350 commits/s ceiling" was 4 × the spawn rate
- [Workflow performance campaign](docs/dev_notes/workflow-perf-campaign.md) — `mix bench.workflow`; a ping TIMEOUT never resets the live control channel (last attempt or a dead-transport error only); `CompactEntity` resolves workflow Entities; `migrate_operative/1` carries `kind:`; retained finished jobs are not intent-mismatch evidence; a stopped operative's writers are closed; a completed workflow drains its owed outbox before teardown; the commit ceiling is the inline fsync on the control-channel reader → `workflow-durable-path-throughput`
- [Operative startup latency](docs/dev_notes/operative-startup-latency.md) — `-p 4` bring-up 365→30 ms; 1000 operatives 9.1 s→1.2 s and their 2000 plugins 57 s→0.24 s: fsync-per-write on the durable hub registry (NOT process_hub's start path) → registry, declared-list precommit AND WorkerQueue registrations group-commit on one `ProcessHub.Service.Batch` core, the manifest is written once per batch; the coordinator's `%Hub{}` was copied into every request task (`Hub.for_workers/1`); partition membership is a metadata index (`ProcessHub.metadata_query/2`), never a registry decode; an enable in flight is not healed (`PluginManager.pending_ids/0`); `PluginManager` claims and the CALLER enables; members start concurrently; the bench preloads code. Measure a start storm by caller-attributed send sizes under a memory cap, never a whole-module trace

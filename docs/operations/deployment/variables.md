# Variables you must set

| Variable | Why a deploy cannot omit it |
|---|---|
| `FLEZHA_DURABILITY_BACKEND` | Unset, it defaults to `none` and `Flezha.State.DurabilityTier.children/0` warns on every boot: this node's disk holds the only copy of its durable state. Setting `none` is the explicit opt-out, byte-identical to a build without the remote tier, reported as `durability: local_only` on `/healthz`. `postgres`, `s3` and `local_path` enable the tier and need their `FLEZHA_DURABILITY_PG_*`, `FLEZHA_DURABILITY_S3_*` or `FLEZHA_DURABILITY_PATH` family; a backend selected without one of those refuses the boot naming the option. Any other spelling resolves to `none` and warns. See [`../remote_durability_tier.md`](../remote_durability_tier.md). |
| `RELEASE_COOKIE` | Unset, `rel/env.sh.eex` mints a random node-local cookie, keeps it `0600` at `${FLEZHA_STATE_DIR}/cookie` (moved with `FLEZHA_COOKIE_FILE`) and reuses it on later boots. That is enough to operate one node, and it is a value no other installation holds. **A cluster still has to set it**: two nodes only connect under one cookie you gave them both. Where the release can neither read nor mint one it starts with `RELEASE_DISTRIBUTION=none`, and every `flz` verb then fails because the CLI reaches the BEAM over distribution. There is still no source-committed fallback. |
| `FLEZHA_SOCKET_FILES_PATH` | The directory runners attach through; share it with every runner container on the node. The entrypoint waits for `<path>/runner_control_channel.sock` as the transport being bound, before it can ask for the readiness verdict. |
| `FLEZHA_NODE_NAME`, `FLEZHA_NODE_HOST` | Form the release node name `RELEASE_NODE=<name>@<host>` (`rel/env.sh.eex`); in Kubernetes the host is the pod IP. |
| `FLEZHA_STATE_DIR`, `FLEZHA_PROCESS_HUB_REGISTRY_ROOT`, `FLEZHA_DLQ_DIR`, `FLEZHA_AUTHZ_DIR`, `FLEZHA_SCHEDULE_DIR`, `FLEZHA_AUDIT_DIR`, `FLEZHA_PLUGIN_ROOT`, `FLEZHA_LOG_PATH` | Every durable path defaults to a **relative** `app_data/*`, resolved against the directory the controller was started from, so it is ephemeral in a container and unwritable under a read-only root filesystem. Point each at a mounted volume owned by uid 1000. The boot prints the absolute state root it resolved to, and says when that directory is empty, so a controller restarted from elsewhere is diagnosable rather than silently cold. |
| `FLEZHA_HEALTHZ_ENABLED` | `/healthz` is off by default; an orchestrator probe needs it on (`FLEZHA_HEALTHZ_PORT` 9569, `FLEZHA_HEALTHZ_BIND` `0.0.0.0`). |
| `FLEZHA_CLUSTER_DISCOVERY` | `manual_discovery` by default; `k8s_pod_discovery` in Kubernetes. |
| `FLEZHA_GRACEFUL_SHUTDOWN_TIMEOUT_MS` | Defaults to `60000`, but the orchestrator's stop grace period must be this plus 15 s (`stop_grace_period: 75s`, `terminationGracePeriodSeconds: 75` in the shipped files). Bump them in lockstep. See [`../graceful_shutdown.md`](../graceful_shutdown.md). |
| `FLEZHA_AUTHZ_ENABLED`, `FLEZHA_TRANSPORT_AUTH`, `FLEZHA_DIST_TLS_OPTFILE`, `FLEZHA_CA_CERT_PATH`, `FLEZHA_SERVER_CERT_PATH`, `FLEZHA_SERVER_KEY_PATH`, `FLEZHA_QUIC_CLIENT_CA` | Authz enforcement is on by default in prod and peer authentication is required by default; turning either off warns on every boot. The TLS material under the cert paths must persist across restarts. Provisioning the cookie, the TLS distribution option file, the QUIC certificates and the bootstrap claim: [`../authn_authz.md`](../authn_authz.md). |
